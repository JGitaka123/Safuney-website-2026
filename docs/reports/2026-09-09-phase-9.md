# Phase 9 — QA, launch, handover

**Date:** 2026-09-09 · **Branch:** `claude/funny-thompson-2lukly` → PR to `main` ·
Plan: `docs/plans/phase-9-qa-launch-handover.md`

The last phase. Everything before it added capability; this one tried to break what was added, wrote
down what a person has to do at three in the morning, and handed the site to people who did not build
it.

## The adversarial pass

Eighteen tests in `apps/web/test/adversarial.test.ts`, one for each attack the brief names. Each asserts
a **defence**, not a feature — the test fails if the protection is removed. That is the difference
between a security note and a security test, and it is why they live in the suite rather than in a
document.

| Attack | What happens |
| ------ | ------------ |
| Price tampering | There is no price parameter to tamper with; the price is read from the database at order time, so a cart held open while a price changes gets the new price |
| Forged callback | Rejected, and the attempt is stored with `signatureOk = false` so it is visible |
| Body altered after signing | Rejected — the classic tamper, tested explicitly |
| Replayed callback | Applied once; three replays change nothing. **Two independent layers**, each asserted separately |
| Short payment | Refused, order stays unpaid, `payment_amount_mismatch` recorded |
| Callback for an unknown payment | Ignored and logged |
| Negative, zero, fractional, absurd quantities | All refused, on add and on update |
| Racing for the last packs | Stock never goes negative, under four concurrent orders |
| XSS in notes and names | Stored as text, never as markup |
| Order enumeration | The access token is long, random, and not derived from the order number |
| Rate limiting | Stops at the allowance, is per-key, and the window slides rather than blocking forever |

**Two of these tests were verified by breaking the code on purpose**, then restoring it. That is how I
found that my first replay test was not testing what I thought it was.

### What that found
The replay test passed with the `eventKey` uniqueness guard disabled — a second layer (the
already-paid check) was catching it. Good news about the system, bad news about the test: it asserted an
outcome that two mechanisms could produce, so removing either left it green. It now asserts each layer
separately, including that four deliveries produce exactly one `WebhookEvent` row.

## A real defect the QA pass found

**The 404 page had been rendering unstyled since Phase 1.** It used colour classes — `text-steel`,
`bg-steel`, `hover:bg-steel-deep` — that were renamed out of the palette when the design system
settled. The heading rendered in the browser default and the call to action was an unstyled link.

The existing test asserted the page was "branded" by checking its text and that a link existed. Both
were true the whole time. The test now asserts computed colour on the heading and the button, which is
what "branded" was always supposed to mean.

**There was also no 500 page at all.** An error anywhere in the app showed Next's default. Both
boundaries now exist: `error.tsx` for a page failure, and `global-error.tsx` for the case where the root
layout itself failed — hand-written CSS in the site's colours, importing nothing from the design system,
because importing the thing that may have just failed is how a fallback becomes a second failure.

Neither page says *what* went wrong. An error message is a gift to anyone probing the site and means
nothing to a customer standing in a kitchen. Both show the digest, which lets our own staff find it in
the logs and identifies nothing on its own. Both tell the customer the one thing they actually worry
about: an order is only placed when they press the button that says so.

## A gap closed while checking one I had documented

The Phase 8 report noted that an order whose 30-minute stock hold expired could still be paid without
re-checking stock. Looking at it properly for this phase: the stock decrement is clamped, so
**stock never goes negative** — that guarantee holds. What actually happens is worse in a quieter way:
the order is marked PAID, fewer units leave than were ordered, and *nothing says so*. The warehouse
finds out at the pick face.

It now records a `stock_shortfall` event with the SKU, what was ordered and what could be taken, so
somebody decides whether to part-ship, back-order or refund instead of discovering it with a box in
their hand. Two tests: one reproduces the race (hold expired, shelf emptied, payment lands anyway) and
asserts both that stock stays at zero and that the shortfall is recorded; the other asserts no event is
written when the stock was there all along. The first was verified by disabling the new code and
watching it go red.

Preventing the oversell outright means re-validating stock inside the payment callback. That is a change
to the money path, and it belongs in a session where the PO is watching rather than slipped in at the
end of the last phase.

## Load

`load/checkout.js` — k6, the brief's target of p95 < 800 ms at 50 concurrent. It walks the read path a
customer moves through, including search, which is the query that touches Postgres hardest.

It deliberately does not place orders: loading the write path would fill a preview database with junk
orders, consume real reserved stock, and hit the payment sandbox's own limits. The write path's risk is
contention rather than throughput, and that is already covered by tests that race concurrent orders for
the last packs.

**Not run in CI**, on purpose: a load test in CI is a flaky test that fails on a busy runner and teaches
everyone to ignore red. `load/README.md` says when to run it and how to read the result.

## Handover

- **`docs/runbooks/launch.md`** — a seven-item gate before anything starts, DNS cut-over with the
  instruction to read the records from `vercel domains inspect` rather than trust any written down,
  Daraja and Paystack go-live, monitoring, rollback (including what a rollback does *not* undo), and the
  seven-day watch with the four things worth watching for.
- **`docs/runbooks/admin-guide.md`** — for the people at Safuney, no technical knowledge assumed. The
  warehouse board, settling invoices, changing prices, publishing products, staff, features, and a "when
  something looks wrong" section for the four things that actually go wrong.
- **`docs/runbooks/catalogue-import.md`** — the spreadsheet round trip, every column explained, and the
  traps that actually bite: Excel eating a leading zero from a SKU, Excel turning a pack size into a
  date, and a stale export silently reverting someone else's price change.

## Not done, and why
- **The domain cut-over itself.** It is the PO's to authorise and it is irreversible for as long as DNS
  takes to propagate. The runbook is ready to execute.
- **Sentry.** Needs a DSN. Until then `vercel logs --follow` is the fallback, and the runbook says so
  rather than leaving someone to discover it.
- **Failed-payment alerts to a phone.** Needs the Africa's Talking key.
- **The load test has not been run against a preview**, because the preview sits behind Vercel
  Deployment Protection and the egress from this environment is blocked. The script is ready; it needs
  someone with browser access or the bypass secret.
- **Screenshots in the admin guide.** The brief asks for them. They would have to be taken against a
  preview I cannot open, and a guide with wrong screenshots is worse than one with none. The text is
  written so it works without them.

## The preview smoke suite is still a no-op
Flagged since Phase 4 and worth repeating, because it looks green and tests nothing. Vercel Deployment
Protection blocks anonymous requests, so every test step in `preview-smoke.yml` skips and the job reports
success. Either disable Vercel Authentication for previews, or set
`VERCEL_AUTOMATION_BYPASS_SECRET` as a GitHub secret. Until then, treat that green tick as decoration.
